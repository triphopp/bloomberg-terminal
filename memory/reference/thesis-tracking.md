# Thesis Tracking — ตัวเลขที่จับตา เทียบค่าคาดการณ์กับค่าจริง

**อัปเดตล่าสุด:** 2026-10-02
**ใช้เมื่อ:** ผู้ใช้สั่งให้ตั้ง / ตรวจตัวเลขที่จับตาใน PORT → TOOLS → TRACK, ถึงวันประกาศตัวเลข, หรือ thesis มี killer condition ที่ยังเป็นแค่ข้อความ
**ใช้กับ:** ทุก agent — MCP ส่งไฟล์นี้ผ่าน tool `get_tracking_spec` · resource `spec://thesis-tracking` (แก้ไฟล์ ไม่ต้องแก้ MCP)
**โค้ด:** `backend/routers/tracking.py` · ตาราง `track_*` ใน `backend/db.py` · แผน `plans/thesis-tracking.md`

---

## 0. หลักการ

1. **คำถาม ≠ ตัวเลขที่จับตา** — คำถามคือสิ่งที่ยังไม่รู้ (`question_*`); ตัวเลขที่จับตาคือสิ่งที่ **จะรู้ในวันที่แน่นอน** (อัตรากำไร, สินค้าคงคลัง, ราคาสัญญา) → `track_*`
2. **ตัวเลขต้องบอกว่าไปอ่านที่ไหน** — ถึงวันแล้วเปิดแหล่งได้ทันที ไม่ต้องค้นใหม่
3. **ทายก่อนรู้ผล** — ค่าคาดการณ์มีเหตุผลกำกับ และตั้ง/แก้หลังตัวเลขออกไม่ได้ (409)
4. **ตัวเลขตัดสินผลเทียบ** — มีช่วงตัวเลข server คิดเอง; ส่ง verdict ขัดกับตัวเลขถูกปฏิเสธ
5. **ไม่ตรง = ต้องหาเหตุผล** — server เปิดคำถาม "ทำไม" เข้าคิว QUESTIONS เอง ตอบตาม `question-research.md`
6. **เส้น killer ไม่ขยับเงียบ ๆ** — แก้ต้องมีเหตุผล และเป็นสิทธิ์ของผู้ใช้ (agent ได้ 403)
7. **แตะเส้น killer ไม่เปลี่ยนสถานะ thesis** — แสดง + ลง timeline (`KILLER_HIT`) ให้ผู้ใช้ตัดสิน

## 1. ตั้งตัวเลข — `track_add`

อ่าน `## Condition Killers` ของ thesis (`get_thesis`) แล้วแตกเป็นตัวเลขทีละตัว หนึ่งตัวเลข = หนึ่งแถว

| ช่อง | ใส่อะไร | ตัวอย่าง (MU) |
|---|---|---|
| `title` | ชื่อตัวเลข | จำนวนวันสินค้าคงคลัง (DIO) |
| `role` | `KILLER` = ข้ามเส้นแล้ว thesis พัง · `WATCH` = จับตา | KILLER |
| `unit` / `definition` | หน่วย และสูตรที่ใช้คิด — คิดแบบเดิมทุกงวด | วัน · สินค้าคงคลังปลายงวด ÷ COGS ไตรมาส × 91 |
| `why` | ตัวเลขนี้บอกอะไรเกี่ยวกับ thesis | สต็อกสะสม = ของเริ่มล้น ราคาจะตามลง |
| `kill_rule` | เงื่อนไข killer เป็นคำ ครบทุกเงื่อนไขประกอบ | DIO > 140 วัน พร้อม finished goods เพิ่ม |
| `kill_op` + `kill_value` | ส่วนที่เป็นตัวเลขของเส้น (`<` `<=` `>` `>=`) | `>` 140 |
| `source_name` | ใครเผยแพร่ / เอกสารอะไร | Micron 10-Q |
| `source_url` | ลิงก์ที่เปิดแล้วถึง | หน้า SEC filings ของ Micron |
| `source_locator` | อยู่ตรงไหนในเอกสาร | Balance sheet → Inventories; Income statement → Cost of goods sold |
| `source_tool` | agent ดึงด้วยอะไร | `get_stock_data(MU, kind=balance-sheet)` · `get_filings(MU, forms=10-Q)` |
| `series_id` | ถ้าระบบเก็บ series นี้เองอยู่แล้ว (`/api/v2/series`) | `dx.contract.dram.ddr4_8gb_1gx8` |
| `question` | Q-ref ของคำถามที่ตัวเลขนี้ช่วยตอบ (คำถาม "ทำไม" จะห้อยใต้ข้อนี้) | Q-0022 |
| `cadence` | `QUARTERLY` `MONTHLY` `WEEKLY` `DAILY` `EVENT` | QUARTERLY |

- บังคับแค่ `title` + `thesis_id`; ที่ขาดขึ้นเป็น `gaps`: `source` (ต้องมีชื่อแหล่ง + ลิงก์ / ตำแหน่ง / tool อย่างน้อยหนึ่ง) · `kill_rule` · `expectation`
- `track_list` ก่อนเพิ่มเสมอ — ชื่อซ้ำใน thesis เดียวกันถูกปฏิเสธ (409)
- เงื่อนไข killer ที่ตรวจด้วยตัวเลขตัวเดียวไม่ได้ ("นาน 4 สัปดาห์", "พร้อม X เพิ่ม") ให้เขียนเต็มใน `kill_rule` — ระบบตรวจได้แค่ "ข้ามเส้น" ผู้ใช้ตัดสินส่วนที่เหลือ

## 2. ตั้งค่าคาดการณ์ — `track_expect`

| ช่อง | บังคับ | หมายเหตุ |
|---|---|---|
| `period` | ✔ | งวดที่ทาย: `FQ1 FY27`, `2026-10` |
| `expected` | ✔ | คาดว่าอะไร เป็นคำ |
| `low` / `high` | — | ช่วงที่ถือว่า "ตรง"; ใส่ข้างเดียวได้ (≥ low หรือ ≤ high); ไม่ใส่ = เชิงคุณภาพ |
| `basis` | ✔ | ทำไมถึงคาดแบบนี้ — guidance, แบบจำลอง, แนวโน้ม พร้อม Z-ref ใน `evidence` ถ้ามี |
| วัน (อย่างใดอย่างหนึ่ง) | ✔ | `date` = D-ref ในปฏิทิน (`question_calendar`) · `new_date` = เพิ่มเหตุการณ์ลงปฏิทิน (title, date, status, source, source_url, kind) · `due_date` = วันที่จะดู เมื่อไม่มีเหตุการณ์ประกาศ |
| `release_time` | — | เวลา เช่น `16:05 ET หลังตลาดปิด` |

- **วันที่เป็นข้อกล่าวอ้าง** — `CONFIRMED` เฉพาะเมื่อผู้เผยแพร่ประกาศวันเอง (ต้องมี `source_url`); ที่เหลือ `ESTIMATED` พร้อมบอกว่าประมาณจากอะไร
- เหตุการณ์เดียวใช้ได้กับหลายตัวเลข (งบ MU หนึ่งครั้ง → GM, DIO, ลูกหนี้): ตัวแรกใช้ `new_date` ตัวถัดไปใช้ `date` = D-ref เดิม
- แก้ค่าคาดการณ์ก่อนตัวเลขออก = เรียก `track_expect` งวดเดิมอีกครั้ง (แถวใหม่ ของเก่ายังอยู่)

## 3. ถึงวัน — `track_due` → อ่านค่า → `track_record`

| ขั้น | ทำอะไร | tool |
|---|---|---|
| 1 | ดูว่าอะไรถึงวัน / ใกล้ถึง / ยังรอคำอธิบาย | `track_due` |
| 2 | เปิดแหล่งตาม `source_tool` / `source_url` + `source_locator` ของแถวนั้น — **ไม่ต้องค้นใหม่** | ตามแหล่ง |
| 3 | คิดตัวเลขตาม `definition` ของแถว (สูตรเดิมทุกงวด) | — |
| 4 | บันทึกหลักฐาน: zettel `EVIDENCE` พร้อม url + quote + วันที่ของข้อมูล | `zettel_search` → `zettel_create` |
| 5 | บันทึกค่าจริง | `track_record` |
| 6 | ถ้า reply มี `opened_question` → ตอบคำถามนั้นตาม `get_question_spec` | `question_*` |
| 7 | ตั้งค่าคาดการณ์งวดถัดไป (เสนอในแชตก่อนถ้าเป็นการทายของผู้ใช้) | `track_expect` |

`track_record`:

| ช่อง | หมายเหตุ |
|---|---|
| `value` | ตัวเลข — ถ้าค่าคาดการณ์มีช่วง server คิดผลเทียบเอง |
| `value_text` | ใช้เมื่อไม่ใช่ตัวเลข หรืออยากเก็บข้อความตามที่ประกาศ |
| `as_of` ✔ | วันที่ของข้อมูล (วันสิ้นงวด หรือวันประกาศ) |
| `zettel` ✔ | Z-ref ที่มี url + quote (หรือส่ง `source_url` + `quote` ตรง ๆ) |
| `verdict` | บังคับเมื่อค่าคาดการณ์ไม่มีช่วงตัวเลข: `IN_LINE` หรือ `OFF` |
| `kill` | ใช้เมื่อเส้น killer เป็นคำล้วน (ไม่มี `kill_op`) |
| `period` | ใช้เมื่อไม่มีค่าคาดการณ์เปิดอยู่ หรือแก้ค่าที่บันทึกไปแล้ว |

ผลเทียบ: `IN_LINE` · `ABOVE` · `BELOW` · `OFF` (ไม่ตรง เชิงคุณภาพ) · `UNSCORED` (ไม่มีค่าคาดการณ์)

ถูกปฏิเสธ (422) → อ่าน `missing` แล้วแก้ทุกข้อ **อย่าเติมช่องให้ผ่านโดยไม่มีของจริง**

## 4. สถานะและป้ายตัวเลข

| สถานะ | เงื่อนไข | ป้าย |
|---|---|---|
| `KILL` | ค่าจริงล่าสุดแตะเส้น killer | แดง |
| `DUE` | ถึงวันแล้ว ยังไม่มีค่าจริง | แดง |
| `OFF` | ไม่ตรง และคำถาม "ทำไม" ยังไม่ชัดเจน | แดง |
| `SETUP` | ยังขาดแหล่งอ่าน / ค่าคาดการณ์รอบถัดไป / เส้น killer | เหลือง |
| `WAITING` | มีค่าคาดการณ์ ยังไม่ถึงวัน | — |
| `RETIRED` | ผู้ใช้เลิกติดตาม | — |

สถานะคำนวณตอนอ่าน ไม่ถูกเก็บ — คำถาม "ทำไม" ที่ผู้ใช้รับรองคำตอบแล้ว หรือเลิกติดตาม ทำให้ `OFF` หาย แต่ผลเทียบของงวดนั้นยังอยู่ในประวัติ

---

## 5. สิ่งที่ agent ทำไม่ได้

- แก้เส้น killer ที่ตั้งไว้แล้ว หรือเปลี่ยน `role` (403) — เสนอในแชต
- เลิกติดตาม / ลบตัวเลข (403)
- เปลี่ยนสถานะ thesis เมื่อแตะเส้น killer — รายงานในแชต พร้อมหลักฐาน
- รับรองคำตอบของคำถาม "ทำไม" — ผู้ใช้รับรองเอง
